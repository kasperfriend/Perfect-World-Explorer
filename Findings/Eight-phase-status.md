- [ ] P3.02 — Reproduce every static-model material and texture-stage state: stage setups, alpha test, blending, transparency, material colors, two-sided flags and the baked-light combination, as a recovered table rather than per-asset special cases. *(18 November, audit of what the table actually covers. **A gap the row above understated, now stated exactly:** `bmd_baked::alpha_test()` is the recovered mapping from `mesh+0x2cc` to `ALPHATEST` and it *refuses* anything but `0xff` with a named error — but nothing calls it. Both builders call only `classify()`, which takes the version, the texture and the two-sided flag, and never sees `0x2cc`. So a mesh whose alpha byte is not `0xff` would go through the enabled-`ALPHATEST` branch's arithmetic (`cutout_reference`) without being refused. That branch is unreachable in practice — the mesh constructor writes `0xff` at `0x7b9408` and no BMD reader writes the field — so this is an uncalled guard, not a live defect; the row says "explicit error" and the error is only reachable from a unit test. **Already proved and not at issue:** the stage-0 colour/alpha ops (`COLOROP(5)`/`ALPHAOP(4)` = `MODULATE2X`/`MODULATE` over `TEXTURE`+`DIFFUSE`), lighting and specular off (`0x7a9759`/`0x7a9762`), stages 1..7 disabled, `diffuse = baked_rgb | mesh+0x2cc<<24`, and that the v5 material block's colours are parsed but never read. **One pass variant is out of scope here and lives under P6:** `0x42c5f3` admits the `WaterEffect == 2` water-quality pass, which `src/scenery_visibility.rs` implements as context (`allows_with_context`/`allows_class_with_context`) with a `WaterEffect` byte that is only settable programmatically — the shipped config is `WaterEffect = 0`. **Not measured:** how many shipped meshes are untextured, since `litmodels.pck` is not staged.)*
- [ ] P3.03 — Handle missing, shared and animated texture references with the client's original lookup rules, page sharing and fallbacks, and explicit dependency errors. *(18 November: the lookup rules are implemented in `src/texture_resolution.rs` in the client's own order — mesh-level skips (length ≤ 4, `nrf_` names), the lowercased manager cache, the `.sdr.` shader-registry names with a terminal miss, archive-before-disk with mount-order duplicates, plain-`fopen` disk fallback, the case-sensitive `Textures`/`Tex_` silent-miss split, and `nrf` derivation with `rf_default.dds`. Its 13 tests were re-run here and pass. **What cannot be re-verified in this checkout, stated as a blocker rather than a claim:** the per-reference census that backs the rule (68,362 references / 4,156 distinct, 4,154 resolving, 2 missing) was measured against `building.pck`, and `litmodels.pck` and `shaders.pck` for the rest. None of the three is staged here — the only packs present are `gfx.pck` (3,499 entries: 638 dds, 11 tga), `trees.pck` (326: 127 dds) and `configs.pck` (59: no textures), and none contains a `building/textures/` member. So the *rules* are proved by their unit tests and by the recorded addresses; the *corpus claims* that every shipped reference resolves, and that `nrf` always takes the absent default, are inherited from the Phase-3 run and not re-measured. **Also blocked on the same absence:** whether any real mesh hits the two mesh-level skips (recorded as zero references) and the `.sdr.` register rows (4 names, 45 refs), which `src/bin/scenery-texture-check.rs` prints when a corpus is staged.)*
- [ ] P3.04 — Trace and implement the client's actual culling, winding and two-sided-material rules instead of a global approximation, including mirrored or negative-scale placements. *(18 November: the **mirrored/negative-scale** half is now *decoded*, and the answer is that the client does **not** compensate for it. Per-mesh submit `0x7b9ca0`, entered from the mesh loop at `0x7a9808`, reads exactly one byte of per-mesh state — `mesh+0x26c` at `0x7a98c5` — and either leaves the pass cull mode alone or calls `CULLMODE(1)` at `0x7a98cf`, restoring the saved `+0x168(%ecx)` value on every exit path. Winding is never rewritten: the index rebase loop at `0x7b9fbc–0x7b9fe1` loads `mesh+0x27c`, adds the vertex base, and stores — no ordering branch. So a mirrored placement's single-sided mesh really does swap `front_facing` in the client and is really culled, and the renderer's current "copy the indices unchanged" behaviour is **correct parity**, not the defect it looks like. `Load` (`0x7bb380`) reads scale/direction/up/position at `+0x44/+0x5c/+0x68/+0x50` straight through and applies no correction either. This was written up the other way round first and withdrawn: reversing the winding would have *diverged* from the client. `src/bin/bmd-sided-gpu-check.rs` already pins the behaviour as device fact. What is **not** established: whether shipped placements ever carry a negative scale or a mirrored determinant at all — `litmodels.pck` is not staged here, so the frequency is unmeasured, not zero — and whether the client applies `scale` to lit-model geometry at render time (its four transform rows are written by `Load` and read back as a matrix by other code, but the submit path `0x7b9ca0` never touches `+0x44`).)*(18 November, separate half: the `bmd_baked` draw-state table's twelve tests now run without a device via `tools/offline_harness.sh bmd-baked`; before this they were reachable only from the six GPU binaries that `#[path]`-include the module.)*
- [ ] P3.05 — Identify and reproduce the real causes of building Z-fighting and overlap: depth bias, draw order, duplicate placements and overlapping geometry behavior. *(18 November: the **depth half is re-verified here against the disassembly**, not inherited. `0x77a250` is the `ZBIAS` setter (`push 0x2f` then `0x77bd00`); it has exactly two call sites in the image, `0x417457` and `0x417475`, which set bias 2 and restore 0 around an effect draw — nothing in the baked path calls it. `0x77a270` is the `ZFUNC` setter (`push 0x17`); it has exactly two call sites, `0x796753` and `0x796cd2`, both behind a `[esi+0x4c]` flag test in the *other* (`0x796xxx`) mesh renderer, so the baked world pass leaves `ZFUNC` at the D3D8 default `LESSEQUAL` and never touches it. The viewer's reversed projection therefore keeps `GREATER` for terrain and `GREATER_EQUAL` for baked scenery, and a coincident duplicate submitted later wins, which is what the client's single depth buffer does. Draw order is the mesh array order (`0x7a9808` loop, one submit per mesh at `0x7b9ca0`). **Blocked, precisely:** the equal-depth census that attributes all 174,744 coincident triangles (168,057 resolved by cull, 6,687 by order, 0 cross-mesh) was produced by `src/bin/bmd-overlap-survey.rs litmodels.pck`, and `litmodels.pck` is not staged here, so that count cannot be re-run.
