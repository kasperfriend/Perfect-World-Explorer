# Viewer performance audit — fresh follow-up

This follow-up lists only newly inspected paths; it does not repeat the previous audit's findings. These are code-confirmed repeated costs, **not measured rankings**. Exact fixes are given for every item; rows marked “implemented” are in the current diff. No FPS gain is claimed without a representative before/after capture.

| # | New cost found | Exact fix | Status |
|---|---|---|---|
| 1 | `weather_gpu::SHADER` called `camera_in_mapped_water` from the vertex shader. Each of 2,880 particle vertices scanned the whole water-area table and mask, although the renderer already computes submerged depth from those same active cells. | Use the renderer’s same `water_depth` result to disable weather for every view when submerged; remove the redundant GPU water-area/mask tables and per-vertex scan. | **Implemented.** This also removes two storage bindings and their uploads. A shader regression test guards against reintroducing the scan. |
| 2 | The weather draw always submitted 480 instances even when only rain or only snow was selected; the disabled species was then hidden in the shader. | Submit instances `0..320` for rain-only, `320..480` for snow-only, and all `0..480` only when both are enabled. | **Implemented**, with range tests. |
| 3 | `apply_attenuation` allocated a temporary update vector and made a second pass over attenuating producers every main-frame update. | Update each producer’s fade and its owner in one pass; preserve the existing “restore only if changed” rule when fading is off. | **Implemented.** |
| 4 | `resolve_attachments` staged one `Result` per hooked producer and formatted a producer-origin string on successful frames, then walked that staging vector again. | Resolve and publish each attachment directly; format error context only on failure, and allocate a detached-ID list only when something actually fails. | **Implemented.** |
| 5 | `LightPublications::publish` linearly searched current-frame entries for every identity, making a frame with many publishers quadratic; `consume_into` also allocated a fresh light vector each frame. | Maintain an identity-to-index map while preserving the entry vector’s insertion order, and reuse a scratch light vector across consumes. | **Implemented.** Existing duplicate-update and insertion-order behavior remains. |
| 6 | Visible water batches were cloned into a new vector, and the sort comparator recalculated each batch’s bounds distance repeatedly. | Store `(distance_squared, batch_index)` once per visible batch, sort the keys far-to-near, and read the immutable batch by index. | **Implemented.** Sorting order is unchanged, including stable ties. |
| 7 | The main view rendered through the water scene target and performed full-frame scene/refraction/depth work even when no visible complex-water batch needed refraction; terrain-depth copying was also unconditional. | Render directly to the final scene target when no visible full-water batch needs refraction. Only update water uniforms, allocate water scene views, copy refraction color/depth, and blit when such a batch exists; copy terrain depth only when a visible reflective plane above the camera needs the edge pass. | **Implemented.** Simple-water-only and no-water views use the direct target path; per-plane water rendering remains unchanged. |
| 8 | `StaticGrid::update` compares the entire cached static-light vector with `lights.lights` on each update, even though the loaded scene-light corpus is normally stable. | Make the corpus immutable after load (or expose mutation only through a revisioned API), and rebuild only on revision change or the existing cell-window movement. Do not replace this with pointer identity while public in-place mutation remains allowed. | **Not changed.** The safe invalidation contract needs an API change; per-frame cost is not profiled. |
| 9 | `world_commands_for_view` creates temporary opaque and SDR `PageSpans` vectors for each view before building the two command lists; the returned lists are also newly allocated each time. | Fold directly over `GpuPage` placement/SDR ranges, or retain reusable scratch spans and command buffers per renderer while preserving original placement order. | **Not changed.** Per-view count and CPU time need measurement first. |
| 10 | Main and refraction command generation use the same view matrix but independently query/sort the whole-world BVH visibility result; only pass admission differs. | Compute visible-order indices once for that matrix and fold that shared list into separate Main and Refraction command lists. Invalidate on matrix/world-index change. | **Not changed.** |
| 11 | Every active `PostGpu::render` creates multiple views and several bind groups for textures that remain the same until resize. | Cache the scene/fogged/warped/downsample/blur views and the finite set of input-pair bind groups when targets are created or resized; select cached groups per post plan. | **Not changed.** The attachments are stable, but the cache needs resize-path coverage. |
| 12 | A camera-key change dispatches the tree LOD compute shader over every placement, including far-off or off-frustum placements; each invocation does bounds/LOD work before indirect append. | Build conservative spatial bins and dispatch only bins whose expanded bounds can intersect the active view/far range; keep a conservative tree-size halo and compare output against the existing CPU LOD reference before enabling. | **Not changed.** The current compute is correct for whole-world placements; savings depend on density and conservative binning. |
| 13 | Weather particle positions, hashes, and camera-relative billboard bases are recalculated in the vertex shader for every scene view (main, reflection, and above-water refraction). | Generate one per-frame camera-relative particle instance buffer, then reuse it for each view while retaining per-view matrix, clipping, and fog. Preserve the existing deterministic particle seed/clock and verify each view against current output. | **Not changed.** More GPU work may shift to a single upload; measure CPU/GPU trade-offs before adopting. |

## Validation boundary

The current implementation changes retain the same weather water-mask predicate, particle clock/seeds, water visibility test, far-to-near water order, and visible-water pass sequence. The current diff has not yet run through CI or a target-machine profile. Validate with the branch Linux tests/formatting and Windows build, then compare the same camera route with/without visible complex water and with rain-only, snow-only, and submerged weather. GPU time and actual frame-time improvements remain unmeasured.
